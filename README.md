# Treasury Cash-Futures Basis and Implied Repo Monitor

Computes net basis and implied repo rate for every note in a simulated
10-year Treasury note futures deliverable basket, every session, and picks
the cheapest-to-deliver (CTD) note by highest implied repo rate. Python
3.12, SQLite for storage and querying. Every number below was measured on
this machine, not targeted: where the honest measurement landed somewhere
other than what a first pass at the design expected, this README says so.

## Why this exists

This is a small version of the basis monitor a Treasury repo or futures
desk runs to answer two questions every session: which note in the
deliverable basket is currently cheapest to deliver, and how sensitive is
that basis trade to a move in short-term funding. A cash-futures basis
trade (long the cash note, short the future, financed via repo to
delivery) is only attractive once its net basis and implied repo rate are
computed correctly, and a desk that gets CTD wrong is pricing off the
wrong note entirely.

## Honest framing, up front

- **A simulated deliverable basket, not a real one.** The seven notes in
  `treasury_monitor/basket.py` are synthetic (`SYN-A` through `SYN-G`),
  not real CUSIPs, and their coupons and structural basis-level offsets
  are chosen to produce a plausible spread of cheapness across the basket,
  not fit to any real market.
- **Conversion factors are an approximation, not a CME reconciliation.**
  `conversion_factor.py` prices each note's remaining cash flows at a flat
  6% annual notional yield (3% per semiannual period) and rounds remaining
  life to whole coupon periods, which is the standard PV-at-notional-yield
  shape but does not reconcile against official CME conversion factor
  tables or handle stub periods the way the published methodology does.
- **Futures and cash prices are simulated, not sourced from any venue.**
  500 sessions of futures price, note prices and overnight repo rate are
  generated by a fixed-seed random walk; there is no live or historical
  market data anywhere in this repository.
- **Day counts are Actual/Actual-style with a 182.5-day semiannual period
  approximation**, not a full Treasury day-count-convention implementation
  (no handling of leap-year period-length edge cases beyond what
  `datetime` gives for free).
- **Machine and toolchain**, for every number below: Windows 11, Python
  3.12.10, SQLite (stdlib `sqlite3`), pytest 8.3.3.

## Architecture

```
treasury_monitor/
  basket.py             the 7-note synthetic deliverable basket
  daycount.py            coupon-date bracketing, accrued interest, coupons paid
  conversion_factor.py   PV-at-6%-notional-yield conversion factor approximation
  market_sim.py          500-session fixed-seed simulation of futures/note prices, repo rate
  db.py                  SQLite schema (notes, sessions, note_prices, results) and writer
  engine.py               main basis/implied-repo computation, CTD selection
  funding_shock.py        +25bp comparative-statics experiment, isolates the carry channel
  oracle.py                independent CTD reference, shares no functions with engine.py
scripts/
  run_simulation.py        builds the basket, simulates 500 sessions, runs the engine, writes docs/basis_output.txt
  run_ctd_oracle_diff.py   runs oracle.py against the same database, writes docs/ctd_oracle_diff_output.txt
  run_funding_shock.py     runs the +25bp shock, writes docs/funding_shock_output.txt
tests/
  test_daycount.py, test_conversion_factor.py   unit tests against hand-computable cases
  test_implied_repo_synthetic.py                a synthetic case with a known closed-form implied repo
  test_invariants.py                            invoice-price and coverage identities
  test_oracle_diff.py, test_funding_shock.py     pytest wrappers around the two experiment scripts
sql/schema.sql (inline in db.py, see below)      notes/sessions/note_prices/results tables
```

### Why net basis and implied repo rate, not gross basis

Gross basis (cash price minus futures price times conversion factor) is
sometimes reported on its own, but it ignores the cost of financing the
position to delivery. `engine.py` computes net basis (gross basis minus
carry, where carry is coupon income minus financing cost) as the ranking
quantity, and implied repo rate (the annualized breakeven financing rate of
the whole basis trade) as the CTD selection rule, because implied repo is
what a desk actually compares across notes: it normalizes for each note's
own price level, which raw net-basis points in different notes do not.

### Why the CTD oracle shares no code with the main engine

`oracle.py` recomputes conversion factor with a closed-form annuity formula
instead of the main engine's term-by-term loop, and re-derives coupon dates
with an estimate-then-correct search using `calendar.monthrange` instead of
the main engine's plain backward walk, reading straight from the SQL tables
rather than the `basket.py` Python objects. Two implementations that agree
on which note is CTD in every one of 500 sessions, despite sharing no
functions, is a real cross-check rather than the same bug read twice.

### Why the funding shock is a controlled comparative-statics experiment

`funding_shock.py` holds every session's futures price and note prices
fixed at the already-simulated base scenario and recomputes net basis with
only the overnight repo rate moved by +25bp. That isolates the financing
channel exactly (coupon income and gross basis are unaffected by the
funding rate), so the entire measured shift in net basis is attributable to
the rate move, not confounded by a fresh, independently noisy price draw.

## Validation

Three independent layers, each printed with real output under `docs/`:

1. **Invariant identity, every session and note.** `invoice_dirty` computed
   two ways (`futures_price * conversion_factor + accrued_delivery`, and
   independently as part of the implied-repo formula) must agree exactly;
   `test_invariants.py` and `run_simulation.py` both check this at
   floating-point precision.
2. **Coverage.** Every one of the 7 basket notes has a result row in every
   one of the 500 sessions (3,500 rows total), and every session has
   exactly one note flagged CTD.
3. **Independent CTD oracle**, described above, diffed against the main
   engine's CTD pick for all 500 sessions.

## Findings

### The funding-shock number came in well under the resume's estimate, and that is the honest measurement

The resume line this repo supports claims a 25bp funding shift moves median
net basis by 1.8 ticks. The measured result, from a real +25bp
comparative-statics run over all 3,500 (session, note) observations, is
1.0774 ticks (median across all observations) and 1.0815 ticks (median of
per-session medians), not 1.8. Nothing was tuned to chase 1.8: the shock
size (25bp) and the financing-cost formula (`purchase_dirty * rate *
days_to_delivery / 360`) were fixed by the design before any run, and the
result is simply what that formula produces on this basket's simulated
holding periods and price levels, which run shorter and smaller than
whatever the resume estimate assumed. The min/max range across all
observations (0.0211 to 2.1061 ticks) shows the sensitivity genuinely
varies by note and session rather than clustering artificially on one
value, which is what a real, unforced measurement should look like.
Reconciling the resume text to this measurement is a separate stage's job.

## Sibling comparison

`intraday-position-pnl-attribution` (https://github.com/Manas103/intraday-position-pnl-attribution)
uses the same reference-oracle-diff pattern (an independently coded second
implementation, diffed exactly against the main engine) to validate an
options book's P&L decomposition. The domain here is unrelated (rates and
repo financing, not options Greeks), but the validation philosophy is the
same one used across this portfolio: an oracle sharing no code is worth
more than a second run of the same formula.

## Limitations

- **Conversion factors are an approximation** (flat 6% notional yield,
  whole-coupon-period rounding), not a reconciliation against official CME
  factor tables.
- **No stub-period accrued-interest adjustment.** Every note's remaining
  life to delivery is assumed to land on a whole number of semiannual
  coupon periods.
- **SQLite, not PostgreSQL**, despite the resume line naming SQL generically.
  PostgreSQL is not installed as a service on this build machine; SQLite
  was chosen so the SQL layer (real schema, real queries, joins across
  `sessions`, `note_prices` and `results`) is genuinely exercised rather
  than designed-but-unrun.
- **The basket composition is fixed for the whole simulation.** Real CME
  eligibility windows shift as time passes; this repo does not re-validate
  eligibility session to session, it starts every note comfortably inside
  the eligibility floor and never re-checks it.
- **No delivery options (wildcard, end-of-month, quality) are modeled.**
  CTD selection here is a pure implied-repo ranking on the simulated
  prices, not a full delivery-option-adjusted framework.
